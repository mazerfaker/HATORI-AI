# Hatoriel 0.6.0 — Voice Foundation Preview
Base: verified successful v0.5.9 commit 861490d (Windows 349, Android 237, iOS 115). Preserve Crimson Core Minimal and all existing inference/storage features.
- Windows: manual reading of last assistant message using installed System.Speech via Windows PowerShell; fixed command, message via UTF-8 stdin, no shell interpolation; stop kills child; cap 4000 characters. No Windows STT yet. Availability of Ukrainian voice depends on installed SAPI voices.
- Android: explicit confirmation before launching system RecognizerIntent; requests offline preference but the provider may ignore it. No automatic submission. Draft appended with cap. Local TTS selects a voice marked not network-required and installed, supports Ukrainian/English, manual play/stop. No mic access directly by app, no recording stored by app. Provider privacy is separate.
- iOS: explicit system permissions, Speech recognition requires on-device capability, 45s recording limit, cancel on scene inactivity, editable draft copied explicitly, system AVSpeechSynthesizer manual play/stop. Speech permissions/voice availability depend on device. No background recording. No audio sent to Hatoriel AI endpoints.
- Next stages: desktop STT, speech feedback state integration, multimodal file ingestion and vision, document extraction. No image analysis or attachments in 0.6.0.
- Acceptance: CI for all three platforms; device tests for permission denial, unsupported language, audio route and interruptions, start/stop, offline availability, draft preservation, and no automatic send. Voice runtime not yet verified. Manual user test deferred to 1.0.

## 0.6.1 Desktop Speech Recognition
Windows local System.Speech desktop recognizer using an explicitly chosen uk-UA/en-US culture, default Windows audio input device, manual start/finish or in-window hold-to-talk. Device selection is through Windows Sound Settings, not a direct microphone picker. No global hotkey, no cloud fallback, no audio files stored by Hatoriel. Requires an installed matching desktop SAPI recognizer; Ukrainian availability is not guaranteed. Windows speech capture has a 45-second recording limit and process watchdog, explicit cancel, focus/page-loss cancellation, bounded UTF-8 transcript protocol and draft insertion only on approval. TTS stops before capture; sending and playback disabled while recording. This is not Whisper integration yet. Two new Rust regression tests for protocol and bounded Unicode draft. Mobile source features unchanged; version numbers aligned. Previous v0.6.0 CI passed Windows #350, Android #238, iOS #116. New CI and actual microphone runtime remain pending.

## 0.6.2 Voice Conversation Mode Preview
Opt-in, session-only voice dialogue on Windows, Android and iOS. Start dictation explicitly, review/insert the recognized text, press Send, automatically read the newly completed assistant response with the selected system voice, then return to an idle state. No continuous listening, wake word, automatic microphone restart or automatic text submission. Typing is also allowed in dialogue mode. Stop audio before explicit capture, suppress auto-read after cancellation, failure, leaving the active chat/background or turning mode off. Windows suppresses typing sounds during an auto-read turn and uses selected speech language for TTS. Android ties playback to the current generation job and foreground activity; iOS ties playback to generation completion revision and active scene, and exposes permission-request state. System recognizer/voice availability and audio device behavior remain platform dependent; Android dictation provider may use a network. No true acoustic echo cancellation or full-duplex barge-in yet. Existing manual input/playback retained; no image or file features yet. Verify CI, permissions, explicit starts, cancellation, one playback per generation, no playback after background, retry, unavailable voice, and no auto-submit. Previous v0.6.1 CI still running at implementation start; no new runtime success claimed.

## 0.6.3 Neural TTS Preview (Windows)
Optional local Piper integration using an explicitly configured, trusted Python executable with piper-tts installed and an existing ONNX voice plus matching .onnx.json. Reference: https://github.com/OHF-Voice/piper1-gpl/blob/main/docs/CLI.md and src/piper/__main__.py. No bundled Python, Piper, model, voice cloning or automatic downloads. Install runtime separately from its official source in a dedicated Python environment; respect Piper GPL and voice-specific licenses. Select the Python executable and model in the Neural TTS panel, adjust speed (0.65–1.5x) and volume, then test voice. Language/timbre depend on chosen model; independent pitch/intonation controls are not implemented. The selected runtime is executable code and must be trusted. The app does not enforce a network sandbox around user-installed Python. The text is supplied over stdin, not command interpolation; fixed CLI parameters; temporary WAV in random directory; bounded input 4000 Unicode characters, synthesis timeout 120s, playback timeout 360s, 64 MiB output cap checked during polling, basic RIFF/WAVE check, cleanup on completion/cancel/normal exit (crashes can leave temp WAV). Audio uses Windows SoundPlayer. Neural errors are visible; no silent system-voice fallback. Existing system TTS and mobile voice mode unchanged. Three new Rust tests for settings, config suffix and basic WAV validation; actual neural playback and CI still unverified. Previous 0.6.2 CI in progress at start; 0.6.1 Windows/iOS cancelled by newer push, Android successful. No neural runtime on mobile yet.

## 0.6.5 Attachments & Drag and Drop Preview
Windows: native file picker, drag/drop regular files, explicit clipboard image paste and Ctrl+V in composer (image clipboard only). Mobile: native document picker and horizontal draft cards. PNG/JPEG thumbnails within 4096×4096 source limits, metadata for other files, duplicate rejection, remove/clear, four files max, 8 MiB each and 24 MiB total. Contents retained in memory only and never sent to model or bridge. Text send blocked until draft attachments are removed. Desktop clears attachments when switching chats; mobile drafts are session-only and Android activity recreation discards them. No PDF extraction, OCR, vision, model upload, chat attachment persistence or mobile drag/drop yet. Desktop uses optional image/rfd/arboard dependencies; file reads bounded, mobile reads on workers. Preview decode and Windows file/clipboard reading may briefly block UI; native clipboard API can allocate before size validation. Device tests and new CI pending. Prior v0.6.4 CI running at start. Next: explicit vision capability and opt-in payload delivery.

## 0.6.6 Vision & Image Analysis (Windows preview)
Desktop Ollama vision uses the selected model, explicit confirmation for each image request, PNG/JPEG validated by existing thumbnail decoder, normalized JPEG with maximum dimension 1536, no EXIF or filename sent, max four images, 4 MiB normalized per image, 12 MiB combined. The shared Rust backend sends base64 images only in the final user message, verifies /api/show advertises vision and rejects obvious cloud/remote markers, disables proxies and redirects, targets fixed loopback, bounds capability and response bytes. See https://docs.ollama.com/capabilities/vision. Requires an installed compatible model and trusted local Ollama service; the app cannot verify that a third-party service actually performs all inference offline. No cloud fallback, no automatic image sending, no attachment bytes in history or sync. Ordinary text path unchanged; images removed from draft on submission, including failed generation (must reattach); re-encoding on UI thread may briefly pause. Cancellation cooperative while streaming; capability/network waits remain bounded by request timeout. Mobile image drafts unchanged, native llama-server vision and bridge image transport not yet supported. No OCR accuracy guarantee. Two shared regression tests for request scope and unsupported model/payload; previous 0.6.5 CI in progress at implementation start. Compilation and actual image inference pending.

## 0.6.7 Document Analysis (Windows preview)
Local extraction of UTF-8/BOM UTF-16 plain text, Markdown, CSV/JSON and common source code extensions; DOCX main document XML via bounded ZIP/XML reader; PDF via explicitly configured trusted Poppler pdftotext executable (stdin/stdout, first 50 pages, 20s timeout, 1 MiB output). PDF tool is not bundled; no OCR or scanned PDFs; no DOCX embedded objects, headers, footnotes or formatting fidelity. Up to four documents within existing attachment limits; each extract capped at 200k Unicode characters and split into 5k-character excerpts. Worker parses in background, stale preview discarded after draft changes. User reviews/selects a single excerpt, explicitly sends it with query to existing local backend (Ollama or llama-server). Reference attached only to current inference messages, not stored as attachment/history or memory suggestion. Answers can quote text and are saved as ordinary chat messages. Untrusted document instructions marked as data; this is not a complete prompt injection defense. No tools executed from document text. No whole-document RAG or mobile extraction yet. Previous v0.6.6 CI still running; 0.6.5 CI cancelled by newer push. Added three parser tests. CI and device/runtime behavior pending. Reference: https://manpages.debian.org/bookworm/poppler-utils/pdftotext.1.en.html

## 0.6.8 Multimodal Context Engine (Windows preview)
Shared Rust lexical retrieval of up to 160 extracted passages, Unicode case-insensitive exact terms, rarity weighting and deterministic ties. User explicitly requests ranking, reviews and selects up to three excerpts, with combined exact preview and 16k-character reference cap. No vector embeddings or automatic whole-document synthesis; no matches means manual selection. Mixed PNG/JPEG + supported documents can be sent together after the reviewed-context button, only with trusted local Ollama vision; documents alone work with existing Ollama/llama-server. Voice dictation is ordinary editable text. Existing profile, personality, memory and recent chat preparation retained. One-turn reference injection, no raw attachment persistence, no automatic upload. Configurable character budget 8k–32k (default 24k), estimated visual headroom 1k characters per image; older chat turns trimmed first, current query/system/reviewed excerpts never silently cut by new budget function; request fails if too large. Character budget is not model token count and cannot guarantee fit in model context window. User must reattach on failed inference; no mobile mixed transport yet. Four shared regression tests for rank/budget. Prior v0.6.7 CI still running when started. New CI and runtime validation pending. Next v0.6.9 stability: fix all actual build failures, avoid superseding latest run, inspect full logs, verify artifact packaging and document limitations.
